## 1. Escopo e decisões fechadas

- Uma API Spring Boot com os cinco endpoints da atividade, segurança com `JdbcUserDetailsManager`, métricas, Swagger e dashboard Grafana.
- Java 21, Maven Wrapper, H2 em arquivo e Docker Compose com aplicação, Prometheus e Grafana.
- HTTP Basic nas rotas restritas. `POST /login` valida credenciais e retorna 200 ou 401, sem token ou sessão.
- Bloqueio na segunda falha consecutiva de `POST /login`. Um login válido zera as falhas. Somente o desbloqueio administrativo remove um bloqueio existente.
- Todas as tabelas terão `id` numérico gerado automaticamente como chave primária. Relacionamentos usarão esses IDs como FKs.
- `{userid}` significa `usuarios.id`, nunca username.
- Senhas armazenadas como hash BCrypt. Ampliar a coluna de armazenamento é uma correção necessária, sem alterar os campos JSON pedidos.
- Contadores de logins válidos e inválidos em memória, reiniciados com a aplicação. Quantidade atual de bloqueados obtida do banco.
- Duas contas iniciais somente no perfil `demo`: `admin` / `Admin123!`, com `ROLE_ADMIN`; `manutencao` / `Manut123!`, com `ROLE_MANUTENCAO`.
- Novos usuários recebem apenas `ROLE_USER`, sem privilégios administrativos ou de manutenção. Essa authority é suporte técnico ao carregamento pelo Spring Security JDBC, que rejeita usuários sem authorities; não haverá endpoint para gerenciar roles.
- Entrega em repositório público, incluindo README, print real do Grafana e JSON exportado/importável do dashboard.

Não implementar frontend próprio, JWT, recuperação de senha, envio de e-mail, gestão de roles, exclusão de usuários, paginação, auditoria adicional, Loki, tracing, Kubernetes, outros microserviços, JPA ou framework de migrações. Usar a organização simples controller → service → JDBC; não criar interfaces e camadas sem necessidade.

## 2. Contratos de implementação

### 2.1. Banco de dados

Criar `src/main/resources/schema.sql` com DDL H2 idempotente, nesta ordem:

| Tabela | Colunas e restrições |
| --- | --- |
| `usuarios` | `id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`; `username VARCHAR(100) NOT NULL UNIQUE`; `senha VARCHAR(255) NOT NULL`; `enabled BOOLEAN NOT NULL DEFAULT TRUE` |
| `login_attempts` | `id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`; `usuario_id BIGINT NOT NULL UNIQUE REFERENCES usuarios(id)`; `failed_attempts INT NOT NULL DEFAULT 0`; `locked BOOLEAN NOT NULL DEFAULT FALSE`; `last_failed_at TIMESTAMP NULL`; `locked_at TIMESTAMP NULL`; `updated_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP` |
| `authorities` | `id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`; `usuario_id BIGINT NOT NULL REFERENCES usuarios(id)`; `authority VARCHAR(50) NOT NULL`; `UNIQUE(usuario_id, authority)` |

São adaptações do SQL da atividade: corrigir a vírgula final; adicionar os IDs; manter username único em `usuarios`; substituir o username de `login_attempts` pela FK `usuario_id`; ampliar o campo do hash; acrescentar `enabled` e `authorities` para o Spring Security JDBC. Não manter uma segunda cópia do username nas tabelas relacionadas.

Usuário inexistente não gera registro em `login_attempts`, pois não há ID válido para a FK. Sua tentativa de login continua retornando 401 e incrementando a métrica de inválidos.

Banco local: `jdbc:h2:file:./data/av2db`. No container: `jdbc:h2:file:/app/data/av2db`, com volume persistente. Testes: H2 em memória, isolado do banco de demonstração. Não habilitar console H2.

### 2.2. HTTP e autorização

Preservar os caminhos exatos do enunciado, inclusive a raiz `/`.

| Método e rota | Entrada | Acesso | Sucesso | Falhas relevantes |
| --- | --- | --- | --- | --- |
| `POST /login` | `{"username":"...","senha":"..."}` | Público | 200, corpo vazio | 400 para JSON inválido; 401 para credenciais inválidas, usuário inexistente ou bloqueado |
| `PUT /trocarsenha/{userid}` | `{"atual":"...","nova":"..."}` | Público, validando senha atual | 204 | 400 para entrada inválida; 401 para senha atual incorreta; 404 para ID inexistente |
| `POST /` | `{"username":"...","senha":"..."}` | `ROLE_MANUTENCAO` | 201 e `{"id":123,"username":"..."}` | 400 para entrada inválida; 401 sem autenticação válida; 403 sem a role; 409 para username já cadastrado |
| `PUT /unlock/{userid}` | Sem corpo | `ROLE_ADMIN` | 204 | 400 para ID inválido; 401/403 por autenticação/autorização; 404 para ID inexistente |
| `GET /` | Sem corpo | `ROLE_MANUTENCAO` | 200 e array de objetos `{"id":123,"username":"..."}` | 401/403 por autenticação/autorização |

- Nunca retornar senha ou hash, nem registrá-los em logs.
- IDs devem ser inteiros positivos. Username obrigatório, com até 100 caracteres. Senhas obrigatórias; validar o limite de entrada de 72 bytes do BCrypt, retornando 400 em vez de erro interno quando excedido. Não inventar política de complexidade de senha.
- Usar erros JSON simples, com campo `mensagem`; não criar um catálogo de erros ou framework próprio.
- Não emitir token, cookie de sessão ou formulário de login. HTTP Basic é stateless. Configurar CSRF de acordo com esta API de demonstração, sem sessão/cookies.
- `ROLE_ADMIN` não implica `ROLE_MANUTENCAO`. Uma autenticação válida sem a role exigida retorna 403 e não é falha de senha.
- Swagger, OpenAPI, health e coleta Prometheus acessíveis no ambiente local de demonstração. Expor somente os endpoints Actuator necessários: `health` e `prometheus`.
- Operações desconhecidas devem ser negadas; não criar endpoints adicionais de negócio.

### 2.3. Login, senha e bloqueio

1. Buscar o usuário pelo username e verificar o bloqueio persistido.
2. Se inexistente ou já bloqueado, retornar 401 genérico. A tentativa é um login inválido; não criar usuário nem desbloquear a conta.
3. Para usuário existente e desbloqueado, validar senha usando o mecanismo Spring Security/JDBC e o mesmo `PasswordEncoder` usado no cadastro.
4. Senha incorreta incrementa `failed_attempts`, atualiza os timestamps e, ao atingir 2, define `locked = TRUE` e `locked_at`.
5. Login correto zera as falhas e limpa os timestamps de falha, retornando 200.
6. O desbloqueio zera falhas, limpa `last_failed_at` e `locked_at`, define `locked = FALSE` e atualiza `updated_at`. Para conta já desbloqueada, continua retornando 204.
7. Troca de senha busca pelo ID, verifica `atual` com BCrypt e grava o hash de `nova`. Não exige Basic, não altera roles e não remove bloqueio. A conta bloqueada pode trocar sua senha correta, mas continua bloqueada.
8. O HTTP Basic consulta o estado de bloqueio e rejeita contas bloqueadas, inclusive com senha correta. As métricas e a sequência de tentativas desta atividade são de `POST /login`: requisições Basic não incrementam esses contadores nem zeram as falhas do login.
9. JSON malformado, erros de validação, troca de senha e falta de role não entram nas métricas de login.

Preservar falhas e bloqueios quando a resposta for 401: não deixar uma exceção de autenticação desfazer a transação que atualizou `login_attempts`. Serializar as atualizações de um mesmo usuário com transação e bloqueio de linha JDBC, sem Redis ou locks distribuídos. Não manter um cache de autenticação que ignore alterações de senha/bloqueio.

### 2.4. JdbcUserDetailsManager

Adaptar as consultas de leitura e os comandos usados pelo cadastro ao esquema acima. As consultas de usuário retornam username, senha e enabled nessa ordem, ainda que a PK seja numérica. Consultar `authorities` por JOIN com `usuarios` e gravar a role usando o ID obtido do username. A consulta de autenticação deve considerar `login_attempts.locked`, além de `usuarios.enabled`.

Criar usuário e sua authority na mesma transação por `JdbcUserDetailsManager.createUser`. Não substituir o manager por uma autenticação que ignora roles.

O método `changePassword` do manager usa o usuário do SecurityContext. Para a troca pública por `{userid}`, verificar a senha atual e atualizar por ID via JDBC é suficiente e evita depender desse contexto. Não implementar métodos de gestão de usuários que a atividade não usa.

### 2.5. Métricas e dashboard

O contrato compartilhado será uma classe concreta `br.com.sensato.av2.observabilidade.LoginMetrics`, com métodos públicos `loginValido()` e `loginInvalido()`, sem interface adicional.

| Registro Micrometer | Nome exposto ao Prometheus | Tipo e significado |
| --- | --- | --- |
| `seguranca.logins.validos` | `seguranca_logins_validos_total` | Counter: POST /login que retornou 200 |
| `seguranca.logins.invalidos` | `seguranca_logins_invalidos_total` | Counter: POST /login que retornou 401, incluindo inexistente/bloqueado |
| `seguranca.usuarios.bloqueados` | `seguranca_usuarios_bloqueados` | Gauge: `COUNT(*) FROM login_attempts WHERE locked = TRUE` |

Registrar as três métricas na inicialização, mesmo sem logins. O gauge consulta o banco na coleta, inclusive após reinício. Não adicionar labels com username ou tabelas para persistir os contadores. Registrar cada resultado de login uma única vez.

Dashboard: exatamente três painéis Stat com essas consultas, atualização de 5 segundos, sem gráficos ou alertas extras. Consultas `sum(seguranca_logins_validos_total)`, `sum(seguranca_logins_invalidos_total)` e `sum(seguranca_usuarios_bloqueados)`. Os dois primeiros indicam totais desde o início do processo, não totais históricos persistentes.

Datasource Prometheus com UID `prometheus`; dashboard com UID `av2-seguranca`. Coleta a cada 5 segundos, usando `http://app:8080/actuator/prometheus`. Grafana acessa `http://prometheus:9090`.
